1전체 그림 — 한 장

한 문장

사람 손 → leader 서보 → 토픽 → follower 서보가 실시간 경로다. 같은 토픽들을 바이트째로 bag에 적어 오프라인에서 데이터셋·정책으로 굽고, 정책이 teleop과 똑같은 토픽에 명령을 쏘면 사람이 빠진 자리에 들어간다.

2환경이 둘, 계약이 하나

이 레포를 헷갈리게 만드는 첫 번째 사실. 파이썬 환경이 둘이고 서로 겹치지 않는다.

환경주는 것진입

source install/setup.bash
pixi lerobot
lerobot 0.5.1 + torch		 lerobot, torch, CUDA pixi run -e lerobot …

대부분의 단계는 한쪽에만 있다. 그런데 두 지점은 양쪽을 동시에 요구한다:

  • converter.cli — rosbag2_py(ROS)로 bag을 읽고 lerobot(pixi)으로 데이터셋을 쓴다
  • sync_inference_node — rclpy(ROS)로 토픽을 받고 torch(pixi)로 추론한다
함정 1 — PYTHONPATH를 덮어쓰지 말 것

ROS를 source하면 ROS 항목이 PYTHONPATH에 올라가고 pixi 환경이 그것을 상속한다. 덮어쓰면 rosbag2_py가 사라진다. 반드시 append:

export PYTHONPATH="$PWD/src/converter:$PYTHONPATH"   # O
export PYTHONPATH="$PWD/src/converter"                # X — ROS 항목 소실

계약: so101.yaml이 유일한 근거

src/converter/config/so101.yaml 한 파일이 아래 전부를 지정한다. recorder·converter·inference가 같은 이 파일을 읽는다 — 그래서 세 계층이 조용히 어긋날 수 없다. 흐름에 대한 어떤 질문이든 이 파일에서 출발하면 답이 나온다.

action이 무엇인지 정확히

action은 follower의 실제 각도가 아니라 명령받은 각도 (/follower/forward_controller/commands)다. ACT가 배우는 것은 "이 관측에서 사람이 무엇을 명령했나"이므로 명령 쪽이 맞다. follower의 실제 각도는 observation.state로 들어간다.

3설치 — 새 PC 기준

필요한 것: Ubuntu 24.04 + ROS 2 Jazzy(/opt/ros/jazzy), USB로 연결된 SO-101 leader + follower, 카메라 2대(손목 + 3인칭 고정). 학습까지 하려면 CUDA GPU.

# 1) 시스템 도구
sudo apt install python3-rosdep python3-colcon-common-extensions
sudo rosdep init 2>/dev/null; rosdep update

# 2) Pixi (LeRobot 계층. sudo 불필요)
curl -fsSL https://pixi.sh/install.sh | bash
export PATH="$HOME/.pixi/bin:$PATH"     # 또는 새 셸

# 3) 클론 + ROS 계층 빌드
git clone git@github.com:dsafjk0024/so101-ros.git
cd so101-ros
source /opt/ros/jazzy/setup.bash
rosdep install --from-paths src --ignore-src -r -y   # 카메라 드라이버(usb_cam·v4l2_camera)도 여기서 깔림
colcon build --base-paths src --symlink-install
source install/setup.bash

# 4) LeRobot 계층
pixi install -e lerobot        # lerobot 0.5.1 + torch(cuda). 몇 분 걸림
pixi run -e lerobot lerobot-info   # 확인: 0.5.1 · CUDA · GPU 인식
함정 2 — --symlink-install은 선택이 아니다

converter.config.DEFAULT_CONFIG_PATH가 Path(__file__).parents[1]/"config" 로 소스 트리를 가리킨다. 심링크 빌드에서는 맞지만, 일반 빌드에서는 site-packages 아래로 복사되어 기본 config 경로가 깨진다. 항상 --symlink-install로 빌드할 것. (우회: recorder는 노드 파라미터 config_path로 명시 가능.)

USB 포트 이름 — udev 규칙을 만들어 두는 편이 낫다

launch 기본값이 /dev/so101_leader · /dev/so101_follower다. udev 심링크를 만들지 않았으면 매번 leader_usb:=/dev/ttyACM0처럼 실제 경로를 넘겨야 하고, 재부팅할 때마다 두 팔의 번호가 바뀔 수 있다. 시리얼 번호 기준으로 고정 심링크를 만들어 두면 이후 모든 명령이 짧아진다.

4모터 셋업 + 캘리브레이션

ROS로 실물을 제어하기 전에 반드시 해야 한다. 모터 ID와 homing 값을 서보 EEPROM에 기록하는 작업이고, HF LeRobot의 네이티브 CLI를 쓴다(ROS 무관). 로봇을 최종 설치할 위치에서 할 것. 

export PATH="$HOME/.pixi/bin:$PATH"

# 1) USB 포트 찾기
pixi run -e lerobot lerobot-find-port

# 2) 모터 ID 셋업 (일회성 — ID는 영구)
pixi run -e lerobot -- lerobot-setup-motors --robot.type=so101_follower --robot.port=<FOLLOWER_PORT>
pixi run -e lerobot -- lerobot-setup-motors --teleop.type=so101_leader   --teleop.port=<LEADER_PORT>

# 3) 캘리브레이션
pixi run -e lerobot -- lerobot-calibrate --robot.type=so101_follower --robot.port=<FOLLOWER_PORT> --robot.id=my_follower
pixi run -e lerobot -- lerobot-calibrate --teleop.type=so101_leader   --teleop.port=<LEADER_PORT>   --teleop.id=my_leader
언제 다시 해야 하나모터 ID캘리브레이션(homing)
다른 PC로 옮김불필요불필요 — ~/.cache/huggingface/lerobot/calibration/ 복사
팔을 재조립·분해불필요필요
서보 교체필요필요

캘리브 값은 서보 EEPROM(Homing_Offset)에도 써지므로, ROS 드라이버는 이미 보정된 Present_Position을 읽는다. 그래서 joint_config_file은 선택이다 — PID·토크 한계를 손보고 싶을 때만 쓴다(src/feetech_ros2_driver/doc/user.md). 캘리브 폴더는 백업 권장.

5teleop 검증 (mock → 실물)

source /opt/ros/jazzy/setup.bash && source install/setup.bash

# 하드웨어 없이 배선만 확인
ros2 launch bringup teleop.launch.py hardware_type:=mock

# 실물
ros2 launch bringup teleop.launch.py \
  leader_usb:=<LEADER_PORT> follower_usb:=<FOLLOWER_PORT>

leader 팔을 손으로 움직이면 follower가 따라온다. 이 한 줄이 프로세스 8개를 띄운다:

프로세스수명역할
robot_state_publisher ×2상주URDF → /tf, /robot_description
ros2_control_node ×2상주100 Hz 제어 루프. read → update → write
spawner ×3죽는다컨트롤러 로드+활성화 후 종료. ros2 node list에 없는 게 정상
teleop_node상주leader→follower 미러. 3초 지연 후 시작

배선 확인 명령 — 막히면 이 순서로

# 무슨 노드가 살아있나
ros2 node list

# 컨트롤러가 active 인가 (spawner 가 죽은 뒤에도 이걸로 확인)
ros2 control list_controllers -c /follower/controller_manager

# 하드웨어 인터페이스 (leader 에 command 가 '없어야' 정상)
ros2 control list_hardware_interfaces -c /leader/controller_manager

# 토픽이 흐르나 · 몇 Hz 인가
ros2 topic hz /leader/joint_states

# 명령이 실제로 나가나
ros2 topic echo /follower/forward_controller/commands --once
알아 두면 진단이 빨라지는 세 가지
  • leader에는 command_interface가 없다. URDF(xacro)의 variant:=leader가 생성하지 않는다 → leader에 forward_controller를 붙이면 인터페이스 매칭 실패로 활성화가 거부된다(조용히 무시가 아니다).
  • leader는 명령을 못 받으므로 손을 떼면 팔이 처진다. 수집 중에 이 성질이 중요해진다(§7).
  • forward_controller는 마지막 명령을 계속 유지한다. 명령이 끊기면 멈추는 게 아니라 그 자세로 버틴다. 그래서 relay 쪽이 0.25초 침묵을 감지해 퍼블리시를 멈춘다.

6카메라 배선

이미지를 만드는 것은 ROS 카메라 드라이버(usb_cam 등)이고, 이 레포는 그것을 bringup/launch/cameras.launch.py로 감싸 둔다. 이 launch가 토픽 이름·인코딩·해상도를 so101.yaml에서 읽어 노드 네임스페이스를 정하므로, 손으로 ros2 run을 치는 것보다 계약과 어긋날 여지가 없다.

헷갈리기 쉬운 것 — URDF 카메라 인자는 이미지와 무관

bringup은 enable_static_cam:=false, enable_wrist_cam:=false로 URDF를 만든다. 그 xacro 인자들은 TF 프레임만 추가하는 것이고 이미지를 만들지 않는다. 이미지는 카메라 드라이버 노드가 퍼블리시해야 하고, 없으면 recorder가 s를 거부하거나 변환이 traceback으로 죽는다.

띄우기

디바이스 경로는 udev 심링크(99-so101-cameras.rules)로 고정해 두는 것을 강하게 권장한다 — 두 카메라가 동일 모델(같은 idVendor/idProduct, 심지어 펌웨어 시리얼도 SN0001로 동일)이라 USB 포트 위치(KERNELS)로만 구분되고, 규칙이 있으면 /dev/videoN 번호가 재부팅·재연결마다 바뀌어도 /dev/cam_wrist / /dev/cam_top은 항상 맞는 카메라를 가리킨다. wrist_device / top_device의 기본값이 바로 이 두 심링크다. 

sudo cp 99-so101-cameras.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules && sudo udevadm trigger
# 카메라 재연결 후 확인
ls -la /dev/cam_wrist /dev/cam_top

규칙이 아직 없거나 카메라가 다른 모델이면 v4l2-ctl --list-devices로 raw 경로를 찾아 wrist_device:=/dev/videoN으로 직접 넘기면 된다. 

# 카메라만 (기본값 그대로 — 심링크 사용)
ros2 launch bringup cameras.launch.py

# 팔 + 카메라 한 번에 — 수집할 때 쓰는 형태
ros2 launch bringup teleop.launch.py enable_cameras:=true \
  leader_usb:=<L> follower_usb:=<F>

토픽 이름·rgb8·640×480은 인자가 아니다 — so101.yaml에서 유도된다. 계약을 바꾸면 launch가 따라온다(§13). teleop.launch.py에서 카메라가 기본 off인 이유는 hardware_type:=mock 배선 확인을 카메라 없이 하려는 것.

띄운 뒤 반드시 계약을 확인한다 — 드라이버가 조용히 다른 인코딩·크기로 떨어지는 경우가 있고, 그건 변환할 때까지 에러가 아니다:

ros2 topic echo /follower/camera/top/image_raw --field encoding --once   # rgb8 이어야 함
ros2 topic echo /follower/camera/top/image_raw --field width    --once   # 640
ros2 topic echo /follower/camera/top/image_raw --field height   --once   # 480
함정 3 — ros2 topic hz는 큰 Image 토픽에서 믿지 말 것

실제로 걸려서 몇 시간을 버린 것: ros2 topic hz <image 토픽>이 1~3 Hz로 불규칙하게 나와서 커널 소켓 버퍼(net.core.rmem_max)를 의심하고 늘렸는데 효과가 없었다 — 원래 값(212992)으로 되돌려도 실측 결과는 그대로였다. --wall-time 옵션을 줘도 마찬가지로 나쁘게 나온다. 같은 노드의 camera_info(작은 메시지)나 순수 std_msgs/String 퍼블리셔는 hz로도 정확히 30 Hz가 나온다 — hz 도구 자체가 큰 sensor_msgs/Image를 다룰 때 부정확하다는 뜻이지, 전송이 실제로 느린 게 아니다.

신뢰할 수 있는 측정법은 메시지를 직접 세는 것:

timeout 10 ros2 topic echo /follower/camera/wrist/image_raw --field height > /tmp/w.txt
echo "frames: $(($(wc -l < /tmp/w.txt) / 2))"   # 10초 동안 몇 개 왔는지. /10 하면 fps

두 카메라를 동시에 켠 상태로 각각 실행해서 합산 대역폭에서도 떨어지지 않는지 확인할 것 — 한 대씩 볼 때의 숫자는 의미가 없다. 이 레포에서 usb_cam 두 대 동시 실측은 27.4 / 27.5 fps로 정상이었다(목표 30 fps).

카메라 캘리브레이션은 왜 없어도 되나

ACT는 픽셀→액션 end-to-end라서 카메라 캘리브레이션(intrinsic/extrinsic)이 필요 없다. 대신 물리적 고정이 요구사항이다 — 수집과 추론 사이에 카메라를 옮기면 정책이 깨진다.

7에피소드 수집

터미널 3개. 모두 source /opt/ros/jazzy/setup.bash && source install/setup.bash 한 상태로.

ros2 launch bringup teleop.launch.py enable_cameras:=true \

# 터미널 2 — recorder
ros2 run recorder episode_recorder_node --ros-args -p root_dir:=bags

# 터미널 3 — 키보드 제어

수집 루프 — 사람이 하는 일

  1. 물체를 시작 위치에 놓는다 (이 리셋 구간은 녹화되면 안 된다)
  2. s → 시연 → 성공/실패 판단
  3. 성공이면 e, 실패면 d
  4. e/d를 누른 뒤에 leader에서 손을 뗀다 — leader는 명령을 못 받으므로 손을 떼면 팔이 처지고, 그 처지는 동작이 에피소드 끝에 녹화된다
  5. 1로 돌아간다
무엇을 버리고 무엇을 남기나 — 코드에 없는 지식
  • 버린다: 태스크 실패, 물체를 건드려 위치가 틀어짐, 중간에 카메라가 가려짐, 의도치 않은 리셋 동작이 섞임
  • 남긴다: 어설프지만 성공한 시도. 완벽한 궤적만 학습하면 정책이 compounding error에서 복구를 배우지 못한다
  • 사람 판단 게이트는 더 엄격하게가 늘 옳은 유일한 게이트다. 나머지 임계값들과 달리 느슨하게 할 이유가 없다
목표수치 감각
스모크 수집2–3 에피소드. 여기서 대부분의 문제가 드러난다 — 실물 teleop, recorder, bag 내용, 변환 drop율을 한 번에 확인
본 수집50 에피소드 ≈ 시도 70–80회 ≈ 1–2시간
bag 크기480×640×3 × 2캠 × 30 fps ≈ 55 MB/s → 20초 에피소드 ≈ 1.1 GB

첫 수집에서 일부러 확인할 것 3가지

  1. 일부러 실패시켜 보기. 카메라 하나를 USB에서 뽑거나 그 노드를 죽이고 s → start refused: topic(s) missing or stale에 그 토픽 이름이 찍히는지
  2. d 후 다시 s → 같은 ep_NNN이 재사용되는지
  3. e 후 ls bags/ep_000/ → metadata.yaml과 *.mcap이 둘 다 있는지. metadata.yaml이 없는 bag은 읽을 수 없다(에피소드 통째로 손실)
함정 4 — recorder를 두 개 띄우지 말 것

다음 에피소드 번호는 노드 생성 시점에 bags/ep_*를 한 번만 스캔해서 정한다. 두 개를 띄우면 둘 다 같은 번호를 잡아 서로를 덮어쓴다. (노드를 껐다 켜는 것은 안전하다 — 기존 에피소드 뒤부터 이어 붙인다.)

프레임을 만드는 방식 — as-of 고정 그리드

메시지가 올 때마다 프레임을 만들지 않는다. 30 Hz 고정 틱을 놓고, 각 틱마다 feature별로 "그 시각 이전의 가장 최신 샘플"을 쓴다. 그 샘플이 해당 feature의 max_age_s보다 오래됐으면 그 틱을 버린다.

왜 고정 그리드여야 하나

lerobot 0.5.1은 timestamp = frame_index / fps로 시각을 합성하고 실제 bag 시각을 버린다. 그래서 지터가 있는 프레임 열을 넣으면 균일한 간격으로 기록되어 정책이 배우는 관절 속도가 조용히 왜곡된다. 균일함은 만드는 쪽이 보장해야 한다.

같은 이유로 버린 틱의 위치가 중요하다:

분류어디영향
leading첫 프레임 전무해 — 에피소드 앞이 잘릴 뿐
trailing마지막 프레임 후무해 — 뒤가 잘릴 뿐
interior중간위험 — 공백이 정상 간격으로 기록되어 시간축이 왜곡됨. 2% 초과 시 에피소드 스킵

--verbose 출력 읽는 법

ep_000: 587 frames (leading=3 interior=1 trailing=2)
    observation.state: match=100.0% mean_dt=9.9ms  max_dt=12.1ms
    action:            match=100.0% mean_dt=20.1ms max_dt=24.0ms
    observation.images.wrist: match=99.8% mean_dt=36.9ms max_dt=71.2ms
    observation.images.top:   match=99.8% mean_dt=37.1ms max_dt=68.0ms
볼 것판정 기준
interior0에 가까울수록 좋다. span_ticks의 2%를 넘으면 스킵된다
max_dt (이미지)100 ms(=max_age_s)에 근접하면 경고 신호. 다음 수집에서 넘어간다 → USB·카메라 점검
max_dt (state/action)50 ms 기준. relay 50 Hz·컨트롤러 100 Hz면 여유가 크다
drop이 한 토픽에 몰림임계를 올리지 말고 그 토픽을 고칠 것
임계값을 올리고 싶어질 때

--max-interior-drop-frac를 올리는 것은 시간 왜곡을 허용하는 것이고, max_age_s를 올리는 것은 더 오래된 샘플을 프레임에 넣는 것이다. 둘 다 "숫자를 통과시키는" 조치가 아니라 데이터 품질을 낮추는 조치다.

바꿔서 만든 데이터셋은 그 사실을 어딘가 적어 둘 것 — 나중에 정책이 이상할 때 데이터를 의심할 근거가 된다.

함정 5 — act는 pixi에 설치되어 있지 않다

pixi.toml은 lerobot만 설치한다. act/는 레포 안의 로컬 패키지이므로 PYTHONPATH에 $PWD/act를 넣어야 from act import …가 풀린다. 추론 노드도 같은 요구를 갖는다(§10).

첫 실행 때 ResNet18 ImageNet 가중치를 다운로드한다 → 학습 PC에 인터넷이 한 번은 필요하다.

산출물 두 개는 한 몸이다

outputs/act_so101/
├── act_so101.pt     # {"model": state_dict, "config": ACTConfig.__dict__, "step": int}
└── stats.json       # {feature: {"mean": [...], "std": [...]}}   ← MEAN_STD 정규화
체크포인트를 옮길 때 stats.json을 빼먹으면

모델은 (x − mean) / std로 정규화된 입력만 본 적이 있고, 그 mean/std는 이 학습 데이터셋에서 나온 특정 숫자다. 다른 통계로 정규화하면 입력 분포가 어긋난다 — 에러는 안 난다. 정책이 그냥 엉뚱하게 움직인다.

추론 노드는 checkpoint_path의 형제 파일로 stats.json을 찾는다. 둘은 같은 디렉토리에 함께 옮길 것.

스모크 학습에서 확인할 것 4가지

  1. train: N frames, M episodes, image_keys=(...) — 프레임/에피소드 수가 예상과 맞는지. converter가 스킵한 게 있으면 여기서 드러난다
  2. act_so101.pt와 stats.json이 둘 다 생겼는지
  3. stats.json의 observation.state → std에 0에 가까운 항목이 있는지. 있다면 그 관절이 데이터에서 거의 안 움직였다는 뜻 — 태스크 설계나 수집 방식을 되돌아볼 신호(예: gripper를 한 번도 안 씀)
  4. loss가 내려가기는 하는지. 200스텝으로 수렴은 안 되지만 방향은 보인다

chunk_size와 n_action_steps — 추론 성능의 첫 레버

chunk_sizen_action_steps
뜻한 번에 예측하는 스텝 수재질의 전까지 실행하는 스텝 수
기본100100 (학습 스크립트가 chunk_size와 같게 설정)
그래서 기본 설정은 3.3초 open loop다

n_action_steps=100, fps=30이면 추론이 100/30 ≈ 3.3초 동안 새 관측을 보지 않고 미리 뽑아둔 궤적을 실행한다. 물체가 미끄러져도 정책은 큐가 바닥날 때까지 모른다.

정책이 굼뜨거나 실패에서 회복을 못 하면 여기가 첫 레버다. 다만 train_so101.py에 n_action_steps CLI 플래그가 없다 — 스크립트를 고치거나 체크포인트의 config를 바꿔야 한다.

설정재질의 주기계산량반응성
n_action_steps=100 (현재)3.3초가장 적음낮음
n_action_steps=100.33초10배중간

temporal ensembling을 켜려면 temporal_ensemble_coeff를 설정하고 n_action_steps를 반드시 1로 둬야 한다 — 설정 검증이 강제한다.

시작 전 — 이 노드는 실물 검증 이력이 없다

두 환경의 sys.path가 합성된다는 것까지만 확인됐고, 실제 체크포인트 + 실제 토픽으로 돈 적이 없다. 팔 주변을 비우고 Ctrl-C에 손을 올린 채 시작할 것.

안전 절차

  1. teleop과 동시에 띄우지 말 것. 둘 다 같은 토픽에 퍼블리시하면 명령이 번갈아 나가 팔이 요동친다
  2. 먼저 토픽만 확인. ros2 topic echo /follower/forward_controller/commands --once → 값이 6개인지, 관절 범위 안인지
  3. 첫 실행은 짧게. 3.3초 open-loop를 기억할 것 — 이상하게 움직여도 최대 그만큼은 계속된다
  4. 관측이 0.25초 이상 끊기면 노드는 액션 발행을 멈춘다. 그런데 forward_controller는 마지막 명령을 계속 유지하므로 팔은 힘을 풀지 않고 그 자세로 버틴다 — 안전하지만 영원히 그 상태라는 뜻이다. Ctrl-C가 최종 안전장치
함정 6 — control_rate_hz는 데이터셋 fps와 같아야 한다

액션 chunk 안의 값들은 1/fps초 간격이라고 가정된 궤적이다. 꺼내는 빈도(control_rate_hz)가 다르면 궤적이 시간축으로 늘어나거나 줄어든다 — 60 Hz면 두 배 빠르게, 15 Hz면 절반 속도로 움직인다. 에러는 나지 않는다.

기본값 30.0은 so101.yaml의 fps: 30을 따라간 것이지 자동 연동이 아니다. fps를 바꿨다면 이 파라미터를 손으로 맞춰야 한다.

  • 추론의 텐서화 3줄(permute(2,0,1) / 255.0)이 학습 때 LeRobot이 한 변환과 정확히 같은지 미확인. 틀리면 에러 없이 정책이 이상해진다 — stats.json 누락과 증상이 구분되지 않는다
  • 0.02 interior 임계의 실측 근거 없음
  • cameras.launch.py/teleop.launch.py enable_cameras:=true 파일 자체는 아직 실행해 본 적이 없다 — 실물 카메라 2대(usb_cam, 동일 파라미터로 ros2 run 직접 실행) 자체는 검증됐고(§6), launch 파일은 그 호출을 그대로 감싸는 것이라 동작할 것으로 보이지만 launch 경유로 실제로 뜬 적은 없다

확인 방법 하나: 학습 쪽 변환을 직접 읽어 비교한다.

pixi run -e lerobot python -c "
import inspect, lerobot.datasets.utils as u
print(inspect.getsource(u.hf_transform_to_torch))"
레포의 알려진 거친 부분영향
README §9 진행표가 낡음recorder·inference를 "예정"으로 적고 있지만 둘 다 구현되어 있다. README보다 코드를 믿을 것. README §6의 lerobot-train 언급도 낡음 — 학습은 act/tools/train_so101.py
src/converter/가 두 역할을 겸함config.py·decoders.py는 계약 라이브러리(recorder·inference도 씀), grid/convert/cli는 변환 앱이다. 그래서 package.xml에 recorder → converter 의존이 잡히는데 녹화가 변환을 필요로 하는 게 아니다 — 처음 읽을 때 여기서 많이 헷갈린다
DEFAULT_CONFIG_PATH가 소스 트리 의존--symlink-install 없이 빌드하면 깨진다 (§3 함정 2)
obs_builder가 feature 개수를 하드코딩관절 순서·shape는 config에서 읽지만 feature 3개는 고정. 카메라를 추가하면 추론 계층은 손으로 고쳐야 한다 (§13)
bag 타임스탬프는 도착 시각recorder가 raw=True로 받아 header.stamp를 못 읽는다. 모든 토픽에 노드 수신 시각을 찍는다 — 촬영 시각이 아니다

13계약을 바꿔야 할 때의 파급

so101.yaml을 고치는 것은 파이프라인 전체를 고치는 것이다. 핵심은 계약을 읽지 않는 곳이 어디인가다 — 계약 밖(수동 동기화): URDF · *_controllers.yaml · teleop_node.JOINTS · 카메라 노드 설정 · control_rate_hz · obs_builder의 feature 개수.

변경자동으로 따라오는 것손으로 고칠 것무효가 되는 자산

관절 순서가 가장 위험한 변경인 이유

바뀌는 것이 순서뿐이라 shape는 그대로 (6,)다. 타입 검사도, 계약 검증도, drop 회계도 전부 통과한다. teleop_node.JOINTS를 안 고치면 손목 두 관절이 서로 바뀐 채 follower가 움직인다 — 에러 하나 없이.

실전 규칙: canonical 순서는 건드리지 않는다. 게이트들은 빠진 데이터를 잡지 뒤바뀐 데이터는 못 잡는다.

일반 규칙: 계약 항목마다 bag보다 위인지 아래인지가 다르다. fps·max_age_s는 아래(변환 파라미터 → 재변환으로 해결), shape·토픽 목록은 위(수집 파라미터 → 재수집 필요).

14데이터 위생 · 테스트 · 파일 지도

PC를 2대로 나눠 쓸 때

bag은 raw 이미지라 크다(≈55 MB/s). bag은 수집한 PC에 두고 거기서 변환한 뒤, 결과 데이터셋(AV1이라 훨씬 작음)만 학습 PC로 복사한다. 변환에는 ROS가 필요하니 수집 PC 쪽이 맞다. 

bags/       datasets/       outputs/       # 전부 gitignore. git 으로는 안 넘어간다
# 데이터셋 복사 (학습 PC로)
rsync -avh datasets/local/so101_pickplace/ 학습PC:~/so101-ros/datasets/local/so101_pickplace/
# 체크포인트 복사 (추론 PC로) — .pt 와 stats.json 을 '함께'
rsync -avh outputs/act_so101/ 추론PC:~/so101-ros/outputs/act_so101/

테스트

# 변환기 (ROS + pixi 동시)
source /opt/ros/jazzy/setup.bash
export PATH="$HOME/.pixi/bin:$PATH"
pixi run -e lerobot test-converter                  # 실제 AV1 인코딩 1건 포함

# AV1 인코딩 스킵 (빠름)
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 pixi run -e lerobot \
  python -m pytest src/converter/tests -m "not slow"

# ROS 계층 전체
colcon test --base-paths src && colcon test-result --verbose

PYTEST_DISABLE_PLUGIN_AUTOLOAD=1이 필요한 이유: ROS의 PYTHONPATH가 ROS 자신의 pytest 플러그인(launch_testing)을 광고하는데 그 의존성(lark)이 pixi 환경에 없다. tests/(복수)가 pytest 스위트, test/(단수)는 colcon이 돌리는 ament lint 보일러플레이트다.
